# KYROCUT X1 Project Format v1

## Identification

- File extension: .kcx1
- Container: UTF-8 JSON
- Format identifier: kyrocut-project
- Version: 1
- Timebase: rational frames per second
- Canonical clip time: integer frames

## Top-level shape

```json
{
  "format": "kyrocut-project",
  "version": 1,
  "application": "KYROCUT X1",
  "id": "project-id",
  "name": "Untitled project",
  "frameRate": { "numerator": 30, "denominator": 1 },
  "resolution": { "width": 1920, "height": 1080 },
  "media": [],
  "tracks": [],
  "playheadFrame": 0
}
```

## Media references

Each project and media entry has a stable project-local ID, display name, media kind, byte size, MIME type, optional durationFrames and portable locator. An unknown duration is represented as null. The locator is relative to the project asset root or an application-managed asset ID. A project file must not depend on an absolute path from the machine that created it.

The manifest does not embed media bytes. Asset packaging and relinking are separate workflows.

## Tracks

A track has a stable ID, display name, kind, mute and lock state, and an ordered list of clips. The browser foundation stores timelineStartFrame, sourceInFrame and durationFrames as integer frame counts at the project's rational frame rate. Supported v1 kinds are video, audio, graphics and adjustment. Nested-composition and effect tracks may be added in future schema versions.

## Clips

A clip references a media ID and stores:

- timeline start frame
- source in frame
- duration in frames

The timeline end is start + duration. The source out is source in + duration. Clip duration must be greater than zero. Each clip also stores an enabled flag (missing values default to true for early v1 files). A clip's media ID must resolve to an entry in the project's media table.

## Compatibility and migration

Readers must reject unknown major format versions with a clear error. Minor compatible additions may be ignored only when explicitly marked optional. Migrations must be deterministic, preserve unknown data where possible and never silently discard edit decisions.

## Current implementation note

The browser and Rust core now share the same v1 field names and frame-based clip representation. The Rust core serializes and validates the versioned document; the browser validates its input before opening it. The runtime UI may display seconds for convenience, but the manifest is frame-based. Media binaries are still separate, so relinking and asset packaging are required for portable delivery.
